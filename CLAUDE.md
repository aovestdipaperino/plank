# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What plank is

A Rust port of the `ds4_agent` C reference (an interactive coding agent for the DeepSeek V4 Flash model), ported functionality-by-functionality — each C section became an idiomatic Rust module with its own tests. The C reference lives in the `refs/ds4` git submodule and is the **source of truth for wire formats and prompt text**: tool output framing, the DSML tool-call syntax, and the system prompt must stay byte-for-byte identical to the C, because that's what the model was trained on. `tests/c_parity.rs` enforces this against committed fixtures (and against the C source when the submodule is present); regenerate fixtures with `PLANK_REGEN_FIXTURES=1 cargo test`. Hard-won parity and tooling gotchas are cataloged in `FINDINGS.md` — check it before re-deriving a quirk, and add to it when you pin down a new one; anything about the model looping (reasoning cycles, re-issued tool stanzas, the guards) goes in `docs/LOOP-FINDINGS.md` instead. Beware: a `\`-continued Rust string literal strips the next line's leading whitespace — never use continued literals for model-facing text with indentation. DeepSeek/Qwen inference is macOS-only (Metal); Gemma runs anywhere (Metal on macOS, CPU elsewhere).

## Commands

```sh
cargo build                 # debug build (builds the C engine via build.rs when refs/ds4 is present)
cargo test --lib            # unit tests — no model needed, pure logic + EchoEngine
cargo test --lib <name>     # single test by substring filter
cargo fmt
cargo clippy --workspace --all-targets -- -D warnings   # CI gate; pedantic + perf lints are warn-by-default in Cargo.toml but -D warnings makes them fail
```

The pre-commit hook runs `cargo fmt` and the clippy command above (with `-D warnings`, same as CI); fix warnings rather than allowing them. Note clippy only re-lints crates it recompiles, so a cached "clean" run can miss warnings in untouched files — CI compiles fresh, so trust the hook/CI over an incremental local run.

- **With the `refs/ds4` submodule present** (macOS): `build.rs` compiles `libds4core.a`, links Foundation/Metal, and emits the `ds4_engine` cfg. Real inference needs a GGUF model (see `download_model.sh` in `refs/ds4`).
- **Without it** (or with `PLANK_NO_DS4=1`, which skips the C engine even when the submodule is present): plank still builds and tests, using the `EchoEngine` stub and, with the default `gemma` feature, the real `GemmaEngine` — this is the normal dev/CI path. Code touching the native engine must be gated with `#[cfg(ds4_engine)]`.

## Architecture

Read `docs/ARCHITECTURE.md` for the full picture (layer diagram, turn lifecycle, module reference). The essentials:

- **Engine trait boundary** (`engine.rs`): all inference sits behind `Engine` (`generate`, `warm_reset`/`warm_append`/`warm_sync`, `get_kv`/`set_kv`, `count_tokens`, `ctx_size`). `ds4engine.rs` + `ffi.rs` are the real Metal-backed implementation (cfg-gated); `EchoEngine` is the always-available stub that keeps the whole app runnable. `gemmaengine.rs` (feature `gemma`, default on) runs Gemma 4 on the native Rust engine in `crates/gemma-engine` (candle 0.9, no C); unlike `Ds4Engine` it needs neither `refs/ds4` nor macOS. Its chat format follows the GGUF's own template, its KV truncates exactly (so `kv_reuse_probe` reports `live == common`, and `Engine::kv_truncates_exactly` makes the agent skip fork snapshots and ladder rungs), and v1 has no MoE, vision, MTP or `decide` — see `docs/GEMMA.md`.
- **Agent core** (`ui.rs`): the `Agent` struct owns engine, session, tools, and system prompt; `run_turn`/`tui_turn` drive the generate → dispatch tools → feed results loop until a generation emits no tool calls. Slash commands are handled here, in **two parallel paths** (plain stdout REPL and Ratatui TUI) — a change to one usually needs the mirror change in the other.
- **Streaming display** (`viz.rs` → `render.rs`/`tui.rs`, `dsml.rs`): model bytes flow through `viz::StreamRenderer` (detects DSML tool calls, emits banners, splits visible vs. thinking text) into a swappable `RenderSink` — ANSI stdout or the Ratatui `OutputLog`. `dsml.rs` is the strict parser producing executable `ToolCall`s.
- **Tools** (`tools/`): `dispatch` mirrors the C tool table — files, edit (with `[upto]` anchoring), bash (sync + async jobs), web, plus the MCP stdio client (`mcp.rs`, hierarchical `~/.plank/.mcp.json` + `./.mcp.json` configs). `ToolContext::resolve_for_write` (`tools/mod.rs`) is the single write-containment choke point: any new tool that writes a path must resolve it there, so the check and the Seatbelt profile keep sharing `Sandbox::write_roots`. Reads are deliberately uncontained.
- **Sessions & context** (`session.rs`, `compact.rs`, `sysprompt.rs`, `context.rs`): transcript persistence under `~/.plank/kvcache` — one directory for every model, with the family in the transcript extension (`.ds4.kv` / `.ds41.kv`, `session::family_ext`; untagged `.kv` files are renamed to `.ds4.kv` at first launch, top level only) and the GC scoped to the live family via each blob's recorded `model`, so neither model's launch evicts the other's checkpoints — keyed by memorable `adjective-celebrity` ids, where the filename stem is the identity (legacy 40-hex ids still load by prefix; `session_identity_sha` is no longer used for ids) and `validate_name` accepts only ASCII alphanumerics and `-`, the same grammar `is_valid_id_prefix` lists by (`<id>.kv` transcripts alongside `<stem>.kv_raw` KV blobs, each with an advisory `<stem>.json` metadata sidecar carrying lineage, usage counters and pin state, swept at startup by a TTL plus byte-budget GC), compaction (durable summary + verbatim tail), system prompt text, and session-start context (git status, AGENTS.md discovery, date). Only `AGENTS.md` and its personal sibling `AGENTS.local.md` are read (in that order at each level, so the personal file has the final word): at interactive startup `agentsmd.rs` links `AGENTS.md` to a lone `CLAUDE.md` in the project root and offers `/init` when neither exists (Generate is the default; "Don't ask for this folder" records the path in `~/.plank/agentsmd-skip`); headless runs do neither. Only the launch offer's `/init` clears the session afterwards (`InitSource`), because that clear is what rebuilds the context around the `AGENTS.md` just written; a `/init` the user typed keeps the conversation it interrupted. `/init` itself is one static prompt (`Agent::INIT_PROMPT`) running six phases the *model* executes: it interviews the user through the `ask` tool, delegates the codebase survey to a sub-agent through the `agent` tool, then writes `AGENTS.md` and/or `AGENTS.local.md` and summarises. Keeping the phases in the prompt rather than the front end is what lets the plain REPL and the TUI share one path — each installs its own `Asker` and the rest follows; under `--ui console` `ask` fast-fails and the prompt tells the model to proceed on its own judgement.
- **Persistent memory** (`memory.rs`, `memextract.rs`; full writeup in `docs/MEMORY.md`): two flat markdown files, `~/.plank/MEMORY.md` (user scope) and `<cwd>/.plank/MEMORY.md` (project scope), of dated `[type]`-tagged bullets (`user`/`feedback`/`project`/`reference`; untagged legacy lines read as `project`), loaded into session-start context alongside `AGENTS.md`. An advisory `MEMORY.md.meta.json` sidecar (`MetaStore`) carries per-entry `uses`/`last_used`/`pinned` keyed by a hash of the entry text, and per-type character budgets (`select_for_render`) decide what renders, evicting pinned-last, then least-used, then oldest — losing the sidecar just zeroes every counter, never breaks loading. The `remember`/`forget` tools (gated on `tools.remember`) and `/remember`/`/forget` write immediately (a model `forget` is a real deletion through `forget_by_id_to`, the same audited atomic path as `/forget`, recoverable only from `memory-log.jsonl` under reason `forget tool`) but only take effect in context at the next session start, because memory sits in the cached prompt tier and a mid-session rewrite would force a full re-prefill. A background pass (`ExtractState::should_run`, off by `memory.autoExtract`/`memory.extractEveryNTurns`) is *snapshotted* at a turn boundary with no tool calls into a `MemoryJob` queue (`enqueue_memory_job`, gated by mutual exclusion with a model-issued `remember`, a throttle, a minimum turn duration (`memory.minTurnSeconds`, default 30s, which defers a short turn's span rather than discarding it), depth keying, and an uninterrupted turn) and *read* at the next idle moment (`process_memory_job`, from each front end's idle loop; the headless paths drain the queue before exit) — a pass reads only the transcript above its `processed_depth`, and getting that backwards degrades silently into reprocessing everything rather than failing loudly. Before a span becomes a job, `enqueue_memory_job` optionally consults the System-1 gate (`memory.gate`, off by default): a confident "not worth extracting" verdict rejects the span (`ExtractState::reject`) instead of queuing it — finished outright when `memory.heldSpanCap` is `0` (the default), or held for re-judging on a later, larger span otherwise. In the TUI a prompt typed during the reading interrupts it and the job goes back to the front of the queue (`TurnShared::memory_pass`); the pass must never block the prompt. `apply_verdicts`/`apply_verdicts_to` is the single write path for its ADD/UPDATE/DELETE/USED verdicts and the sole place `MetaStore::carry` moves accumulated usage onto a rewritten entry's new id; every automatic change is appended to `~/.plank/memory-log.jsonl`, read back by `/memory log`.
- **System-1 decisions** (`decide.rs`, `Engine::decide`): typed, probabilistic answers read from the logprobs of pre-tokenized answer letters after one forward pass over a question suffix — no tokens generated. Runs on a *dedicated* small-context session, never the live one, so it is outside the KV-cache discipline entirely. `decide.rs` is pure (softmax, abstention rules, index-to-enum mapping) and fully tested without a model; `EchoEngine` scripts verdicts so every consumer stays covered by `cargo test --lib`. The one consumer is the memory-extraction gate (`memory.gate`, off by default). The gate always shows `yes` as A, so a family's prior toward a letter as such biases it; `/memory calibrate` measures that offline by asking saved spans with the letters swapped (`Question::boolean_swapped`, `OrderPair`, `bias_report`) and suggests a per-family `memory.gateBias` added to `gatePercent` — offline because on DeepSeek a second ask re-prefills the span (the decision session cannot be rewound), which the live gate must not pay at turn exit.
- **Skills** (`skills.rs`): a `SKILL.md` directory whose body becomes a user-turn preamble (`$ARGUMENTS` substituted, or appended when absent); the name is the slash command, so no whitespace, `/` or `:`. Six built-ins are compiled in from `src/resources/skills/` and parsed by the same loader as a user's, so a built-in can use nothing a user's skill could not. `load_layered` stacks built-ins, then `~/.plank/skills`, then `./.plank/skills`, each layer replacing the last by name — a project skill *replaces* the built-in of that name, which is why `load_from` stays disk-only: `plugins::gather` loads every plugin's `skills/` through it, and seeding the built-ins there would re-attribute them to each plugin as `<plugin>:<name>`.
- **Plugins** (`plugins.rs`): a plugin is a directory bundling skills, agents, templates, hooks, an `.mcp.json` and a `settings.json`. Scan roots are visited in the order `~/.plank/plugins/claude/`, then `~/.plank/plugins/dev/`, then `./.plank/plugins/`, and a later root wins a name collision: a user-authored dev plugin beats a fetched one, and project plugins outrank both. Both the plank (`.plank-plugin/plugin.json`, `templates/`, `hooks.json`) and Claude Code (`.claude-plugin/plugin.json`, `commands/`, `hooks/hooks.json`) spellings are accepted. Contributions merge into the existing loaders: a plugin entry is always addressable as `<plugin>:<name>` and keeps the bare name only when nothing else claims it — except skills, which are namespaced only (`/plugin:name`, never `/name`). Plugin settings sit below `~/.plank/settings.json`, so a plugin can never override the user, and a plugin `settings.json` cannot set `engine.*`, `worktree.*`, `tools.*` or `pluginConfig` at all: those sections (`PLUGIN_REFUSED_SECTIONS`) are dropped with a warning surfaced through `settings_audit_warnings`. The `claude/` root holds plugins fetched from a git repository, a marketplace repository, or a `.tar.gz` (`claudeplugin.rs`) via `/install-claude-plugin <url|owner/repo> [name] [--force]`; installing rewrites `${CLAUDE_PLUGIN_ROOT}` to the install path because plank's hook runner injects no environment when it execs `/bin/sh`. A plugin may also declare a `profile` block (`docs/PROFILES.md`): with `--profile <name>` it supplies the whole system prompt, an allow-list of builtin tools, a settings layer that may set anything but `engine.*`, and the banner logo, display name and UI accent. Two booleans, `folderContext` and `agentsMd`, default to `false` for a running profile and gate the launch-folder context (git status and project memory, via `profile::folder_context_enabled` and `memory::load_scoped`) and everything `AGENTS.md` (discovery, the `/init` launch offer, `CLAUDE.md` linking, via `profile::agents_md_enabled`); both are always on without `--profile`. A WASM component the running profile bundles (a `wasm` section plus `wasm/<module>`) is the one component offered for trust at launch (`wasmreg::profile_trust_offers`, a Not now / Trust panel in the TUI, `[y/N]` on a terminal stdin in the plain REPL), and only when new, changed or widened; every other component waits for a typed `/plugins trust <id>`. Optional `verbs` / `additionalVerbs` (mutually exclusive; a list for every phase or an object keyed by `profile::VERB_PHASE_KEYS`) replace or extend the status-bar verb pools, read per frame by `status::pick_verb` through `profile::active_verbs`, where a phase left empty keeps its built-ins. An optional `recommendedModel` names an engine used ahead of `engine.model` (never ahead of `--model`) only when its main file is already on disk (`engines::choose_with_recommendation_in`, never a download). A profile's `grids` (MCP server name to WASM component id) is one sanctioned crossing of a component's RAM disk (`docs/WASM-PLUGINS.md`, Grid bridge): the MCP client strips `plank-frame://` resources into `grid::GridStaging`s, and a routed staging opens and blocks synchronously inside the same tool call, reporting what happened in that call's own result (`grid closed: <reply>` / `grid closed without changes` / `grid not opened: <reason>`) rather than through a deferred notice. Grids and `edit_csv` (the `files` capability's tool-invoked editor) both open this way: `frames::run_frame_blocking` (`src/tools/frames.rs`) checks the refusals — outside the TUI, inside a sub-agent, a remote-driven turn, another editor already open, or the component itself (not loaded, no `frame` surface, a screensaver, no `fs` grant) — then lends the whole WASM session to the TUI's busy loop through `FrameBridge` (`src/framebridge.rs`), modal like the `ask` panel, and gets it back when the component closes the frame. Without the flag the same plugin contributes exactly as any other, so the default path — and `tests/c_parity.rs` with it — is untouched. `--profile` also takes a local directory or `owner/repo:folder` (`claudeplugin::Source::GitFolder`): `main.rs`'s `resolve_profile_source` asks, installs into `~/.plank/profiles/`, and launches, and the install's `.plank-source` record (`profiles::find_by_source`) makes the same argument launch the installed copy without asking again, unless the source's manifest now declares a higher `version` (`claudeplugin::source_version` reads only that manifest, `profiles::freshness` compares), in which case it offers an update through `claudeplugin::replace_profile`, which moves the old copy aside and restores it on any failure. HAL lives in the public `aovestdipaperino/plank-profiles` repo, not in `examples/`. `/edit-profile` (`profileedit.rs`) edits the running profile's files in one `/memory`-style buffer and, on a saved change, restarts plank into it by quitting normally and `exec`ing the launch arguments with `/resume <session>` (`profileedit::restart_args`).
- **Model artifacts** (`engines.rs`, `enginemigrate.rs`, `manifest.rs`, `downloader.rs`, `download.rs`): the available engines — each a `main` model plus optional `mtp` and `vision` companions — are declared by `engines.json` at the repo root, compiled in as the offline baseline, fetched from `raw.githubusercontent.com` (3-second timeout, at most once every 24 hours) into `~/.plank/engines.remote.json` when its top-level `version` is higher, and layered under `~/.plank/engines.local.json`, the only layer allowed to point a role at a local `path` (optionally with a `url`, normalised by `engines::download_url`, that only fetches a missing file into that path and never makes the role managed). `--model <name|path>` (or `engine.model`) picks an engine by name, else loads a file; `--model:<name>` must name an engine; with no choice, the catalog `default` (`ds4vision`) is used. `gemma4-e4b` and `gemma4-12b` are main-only catalog engines carrying a `"family": "gemma"` hint, so a not-yet-downloaded Gemma engine still routes to `GemmaEngine` and names `.gemma.kv` transcripts; a Gemma file given by path is classified by its own `general.architecture`. Each engine upgrades by its own monotonic `version`; install paths are derived locally as `~/.plank/<engine>[.mtp|.vision].gguf`, and `enginemigrate` renames the pre-engine layout (`ds4flash.*`, `*.manifest`, `staging-*/`) once at startup. A newer version starts a *detached* helper (`plank --model-downloader`, one per machine via `flock` on `~/.plank/downloads/lock`) that streams each artifact into `~/.plank/staging/<engine>/<role>.part`, hashing SHA-256 as it goes; a resumed `.part` is re-read from disk to rebuild the hasher, because `sha2` has no serializable state. Verified artifacts are installed only at the *next* launch (`downloader::swap_staged`), because a running plank has the ~87 GB model memory-mapped. The one rule that must never break: the staged `<engine>.installed.json` moves **last**, so its presence is the proof that the whole set landed — move it first and an interrupted swap installs a mismatched trio while claiming success. Cancellation is a flag file (`~/.plank/downloads/cancel`), not a signal, so it works from a plank that then exits. A `.ggd` weight delta (`ggufdelta.rs`, format in `crates/gguf-delta`) given as `-m` is swapped for an APFS clone of its base (looked up beside the `.ggd` by the recorded filename, never by path) patched under `~/.plank/models/patched/` before anything reads a model header; the originals are never written, and KV caches are shared with the base on purpose. A delta whose base is a managed engine's main inherits that engine's `id` and companions (`engines::inherit_companions_in`) with `managed_main` false, so the clone is never upgraded; a bare path gets companions only when it is a managed main under another name.
- **KV-cache discipline** (`docs/KV-CACHE.md`: the requirements-to-implementation rationale followed by the layer-by-layer mechanics): `Ds4Engine` keeps one live session across turns so only the new suffix is prefilled; the system prompt has a fingerprinted disk snapshot (`sysprompt-<fp1>.kv_raw`). Reuse only genuinely matching token prefixes: a blob's embedded signature is the sole trust input, its sidecar is advisory, and a stale checkpoint is rebuilt rather than trusted. On top of that, `kvladder.rs` keeps up to 3 KV snapshots ("rungs", `<id>.rung-<n>.kv_raw`) at increasing transcript depths so micro-compaction's in-place tool-result rewrites can restore a rung that predates the edit and extend forward, instead of forcing a full re-prefill; `context.microcompact` (default `true`) disables micro-compaction entirely when off. Rollback, fork, rename and sub-agent sidechains keep the ladder consistent with the transcript: rollback calls `discard_ladder`, fork and `end_subagent_fork` call `KvLadder::truncate_to`, sidechains (gated by `in_sidechain()`) never store the payload or push rungs, but a sidechain pass that would rebuild from zero is rescued first from the innermost `fork_kv` snapshot and then from the ladder (`rescue_prefix_before_rebuild`, off while `alt_engine_depth` is non-zero), and the GC keep set includes the live rungs. The one rule that must never break: a rung is looked up under the fingerprint of the transcript *truncated to the rung's own recorded depth*, never the full current transcript — get it backwards and every rung misses forever, silently, while the feature looks fully wired up.
- **Background job notifications** (`tools/bash.rs`, `docs/BACKGROUND-TASKS.md`): behind `tools.bashNotify`, a bash job that finishes after the model stopped watching it wakes the model with its final observation wrapped in a `<system-reminder>` user message. The table is the sole source of truth: a job the model observed done is removed at that observation, so `BashJobs::take_finished` announces each job at most once. Notifications join the transcript only at a turn boundary (after a tool round, or from the idle loop of each front end), never mid-pass; the TUI skips the idle wake while the editor holds a draft or a modal pane is open.
- **GPU yield** (`gpuyield.rs`, `Engine::can_release_gpu`): a foreground `bash` call whose command exits 75 with a line starting `GPU not available` (every job gets `PLANK_GPU_YIELD=1`), or that wrote a line into its per-run `PLANK_GPU_YIELD_FILE` whatever its exit status (`gpuyield::signal_path`/`take_signal`, the primary signal because a pipe hides the exit status; read and deleted after every foreground run, a background job's at reap), makes `Agent::dispatch_tool` save the session and the KV (a nonce-signed file), drop the engine for an `UnloadedEngine` placeholder (the last `Arc<Ds4Model>` going is what runs `ds4_engine_close`, freeing Metal and `/tmp/ds4.lock`), re-dispatch the call once with the first run's sandbox decision and `BashJobs::wait_to_exit` (it waits for the command to exit, not for `refresh_sec`), reopen through the `ReopenFn` `make_local_engine` built from its resolved parameters (files checked and lock probed first, since the C `exit`s on either; fd 2 goes to `~/.plank/gpu-yield.log`), and `set_kv`; a refused restore re-warms the tiers, a failed reopen keeps the placeholder and retries at the next top-level turn start into whichever slot then holds it (`Engine::is_gpu_placeholder`), never a remembered position. At most two cycles per turn. `!`/`!!` escapes (`Agent::run_bang`, `run_immediate` exports both variables and returns `ImmediateOutput::gpu_signal`) share the cycle through a `CycleRerun` re-run step and a front-end `BangIo`, one cycle per escape outside the turn cap. The engine may sit in `Agent::engine`, `alt_engines` or `parked_engines` (the parent `run_sidechain_on` sets aside). Background jobs never cycle. The model can also ask up front: a `bash` call with `suspend_model` (true, 1 or yes; deliberately undeclared in the trained schema and taught by `sysprompt::GPU_SUSPEND_NOTE`, appended only when a `ReopenFn` exists) runs `gpuyield::run_suspended` through `Agent::dispatch_suspended_bash`, the same cycle with no failed first run, counted against the cap; otherwise it runs normally with a one-line "suspend_model ignored" note.
- **Prompt suggestions** (`suggest.rs`, `suggestions.*`): after each turn, a short sidechain generation off the warm session guesses the next thing the user will type, shown as ghost text in the TUI input (Tab/Right to place, Enter to send, any other key to dismiss). TUI only — the plain REPL has no line to ghost into. `suggest.rs` is pure (the instruction text, the sanitizer that rejects the model answering as itself or a leading `/`, and the idle-slot scheduler) and fully tested without a model; the generation itself runs as a sidechain (`begin_sidechain`/`end_subagent_fork`, mirroring `process_memory_job`) on a worker thread via `tui_quiet_pass`, with its sink forced to `Null` so nothing streams to the screen. The scheduler is the interesting part: a pending suggestion always beats a queued memory job at the idle slot, because a suggestion is worthless once the user types while a memory pass may defer; the memory pass cannot starve, since a suggestion is queued once per turn and its flag clears when it runs, so the waiting job takes the next idle moment. Skipped when the KV would rebuild from zero, which is what makes it affordable on by default (`suggestions.enabled`, default `true`).
- **Front-end selection** (`main.rs`): TTY on both ends → Ratatui TUI; piped → plain line REPL; `--ui console` → headless (one-shot with `-p`, else the stdin protocol); `--ui chart` → headless one-shot that silences stdout for the turn (`SilencedStdout`) and paints only the `/toks` chart on the saved descriptor, live, from a painter thread (`ChartLive`); `--ui quiet` → the same silencing with one line of notes instead, the middle one posted by a `QuietLive` watcher when the first prefill sample marks the handover into generation. `chart` and `quiet` both require `-p`. Slash commands with a pane, such as the interactive `/kvcache` cache browser, need a static text equivalent on the plain-stdout path (`/kvcache pin|unpin|rm|gc`). In the TUI, lines a remote controller queues (`/rc`) wait while a WASM frame is open (`remote_lines_gate`), with one `waiting for the frame to close` dim line sent to the remote, while a queued line dismisses an idle screensaver and runs.
